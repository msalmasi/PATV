# Auto-account escrow (PAT waiting to be claimed)

Status: built on staging (site + bot), **switch OFF** by default. Prod ships dark.

## The idea

When a Camfrog user has no PATV account, Pepe makes one for them automatically (`find_or_create_user` ->
`POST /api/users/camfrog/register`, a `CFxxxxxxxx` username). Those accounts collect free PAT (activity rewards,
achievements, level-ups, raffles, top mic...) that nobody can ever spend on the website, and most of it is never
claimed. The user's direction (2026-10-12):

> keep activity rewards and other PAT earned by autogenerated PATV accounts in escrow and give them 6 months to
> claim it when they create their actual PATV account.

## Decisions

### What an "auto account" is

`autoaccount.js` is the one helper (it replaces the two regexes and the SQL GLOBs that were copied around):

* `AUTO_NAME = /^CF[a-z0-9]{8}$/` - the generator's username, case-sensitive.
* `AUTO_LOGIN = /^cf[a-z0-9]{8}$/i` - a Camfrog *login* that looks like one (any case).
* `AUTO_GLOB` - the same as an SQLite GLOB.
* `users.auto_source` - **provenance**, never cleared: `'camfrog'` for an account Pepe made. Set by
  `/api/users/camfrog/register`; backfilled once for existing rows whose username matches `AUTO_NAME` and whose
  email has no "@" (the generator's random email).

An account is an **auto account right now** (`isAutoAccount`) when all of these hold:

1. `auto_source` is set, and the username still matches `AUTO_NAME`;
2. it has no way for a person to sign in: no email with "@", no Discord or Twitch id, no `sso_links`
   (Google / Plex / Telegram sign-in), no `telegram_links`, no `plex_members` link.

The moment one of those changes, the account has been claimed in place and its escrow is released to it. This is
computed, not a flag someone has to remember to clear, so no sign-in path can forget it.

### What goes to escrow

Only **free rewards**: PAT the protocol hands out for being there, not PAT the person won from other players or
from their own stake. Default list (editable on the admin card):

* site payout flows: `achievements`, `levelup`
* Pepe's credit types (`/api/bonus/chatwinner` `type`): `activity-reward`, `camfrog-raffle`, `camfrog-trivia`,
  `mic-hourly`, `level-up-bonus`, `moan-bonus`, `beg`, `pictionary-win`

**Game winnings stay spendable.** An auto account that stakes its own PAT (a duel, a spin, blackjack, a heist
buy-in) gets the stake back and the winnings in its wallet. Holding them would mean holding the person's own money:
a loss would cost them, a win would be locked, and every game would need to know which half of a payout was stake.
The escrow is about PAT the system gives away to someone who never set up an account - not about taxing play.

**Existing balances are not touched.** Only rewards paid after the switch is turned on go to escrow. The 321M already
in auto wallets was paid under the old rules; taking it back would be a clawback, would break games in progress, and
needs a supply-neutral migration nobody asked for. The stale-account cleanup already deals with dormant balances.

**Welcome PAT stays spendable** (it is the onboarding stake that lets a newcomer try a game). It's a one-line change
on the admin card if the user wants it held too.

### Where it is held

A dedicated table, not the game escrow ledger (`escrow/ledger.js`): those holds are stakes with a settle /
refund lifecycle owned by a game, keyed by Camfrog login and mirrored to Pepe. These are per-account reward entries
with an expiry, keyed by userId, which the merge code moves like any other user row.

```
auto_escrow          id, key (UNIQUE - the credit's transaction id: a retried credit is held once), user_id, login,
                     amount (> 0), kind, source, earned_at, expires_at, state held|claimed|expired, done_at,
                     done_key (the claim / expiry batch), claimed_by, dest (where an expired entry went)
auto_escrow_claims   one row per release: id (= the wallet transaction id), user_id, amount, entries, via, at
auto_escrow_notices  per account: when Pepe last told them, and up to which entry
auto_escrow_meta     enabled / enabled_by / kinds
```

The paying pool is debited exactly as before (the incentive budget, the Reserve claim...): the reward just lands in
`auto_escrow` instead of the wallet.

**Supply:** the held total is its own row, `auto_escrow` ("⏳ Earned in chat, waiting to be claimed"). A hold moves
PAT pool -> escrow, a claim escrow -> wallet, an expiry escrow -> the routed pool, so the total never changes.

### Claiming

When the account stops being an auto account - the person links the Camfrog name to a real account (`!verify`,
Edit profile -> Connections: the auto account is merged into theirs), or the auto account itself gets a sign-in
method - every entry still inside its window is released, in one transaction:

* the entries go `held -> claimed` (guarded on `state = 'held'`, so twice is impossible),
* one wallet row `Claimed: PAT earned in chat` with a deterministic transaction id
  (`aec-<userId>-<last entry id>`) - the same release can't be paid twice,
* an inbox notice: "You had PAT X waiting from chat".

The merge moves the entries with the account (`accountMerge.js` rule), and `afterMerge` releases them right away.
A sweep every 10 minutes catches anything else (an account that got a sign-in method in place, a merge that ran
while the module was busy) and follows `account_merges` for entries whose account is gone.

An auto account merged into **another auto account** (the stale cleanup's duplicate merge) keeps its entries held,
with their original expiry.

The switch only controls **new holds**: switching it off never strands anything - existing entries are still
claimable and still expire.

### The six-month window

**Per entry**: each entry expires six calendar months (UTC) after it was earned (31 Aug -> 28 Feb). A rolling window
per account would let a regular who never claims keep a growing pile forever, which defeats the point; per entry,
"what you earned in chat waits six months" is easy to explain and every entry has one fixed date.

Expiry runs on the site (`autoescrow.tick`, every 10 minutes; idempotent, keyed batches): every held entry whose
`expires_at` has passed goes to the destination of the PAT Routing row **`auto_escrow_expired`** (default: 100% to
the Federal Reserve; an admin can route it elsewhere - the remainder of a split goes to the Fed, as with every row).
While the pools live on the site the move is a pool leg in the same transaction; if they don't, a negative
`reserve_claims` row (`auto_escrow_expired`) that Pepe's funding tick credits to the Reserve (the stale cleanup's
path). Entries are never claimable once `expires_at` has passed, whether or not the job has run yet - so the outcome
never depends on the time of day the job happens to run.

### In chat

* `!balance` shows spendable plus waiting: "you currently have PAT 12,000. PAT 85,000 more is waiting for you -
  claim it at publicaccess.tv within 6 months (!verify)."
* Pepe PMs an auto user **when he sees them** (the stale-notice pattern): at most once every 3 days per account,
  and only when something new was escrowed since the last PM. The site keeps the per-account state
  (`/api/autoescrow/notice-logins`, `/api/autoescrow/notified`); a credit answered `escrowed: true` makes Pepe refresh
  the list early.

### The stale-account cleanup

* Escrowed PAT is **not** counted as the account's balance for the cleanup's tiers or thresholds. It isn't
  spendable, it has its own clock and its own destination; counting it would keep junk accounts alive (the bot-account
  150k rule) on PAT that is going back to the Fed anyway.
* The cleanup only ever touches `users.points_balance`; the escrow only ever touches `auto_escrow`. The two never
  reclaim the same PAT. Archiving leaves the entries alone; restoring doesn't touch them.
* **Purge** skips an account that still has held entries: deleting the account would make the PAT unclaimable before
  its six months are up. It is purged by a later run once its entries are claimed or expired.

### Admin

`/admin/economy#autoescrow` (admins): the switch, held totals (PAT / entries / accounts), the top accounts, what
expires in the next 30 days, claimed vs expired by month, the escrowed kinds (editable). Changes are audit-logged
(`admin_audit` action `autoescrow.settings`).

## Tests

`test/autoescrow.test.js`: earn -> escrow; claim on link -> released once (twice is a no-op); expiry -> the Fed;
game-stake winnings stay spendable; the cleanup's purge skips held entries and archive / escrow never double-reclaim;
an account merge (auto -> real releases, auto -> auto keeps); expiry independent of the time of day it runs; supply
unchanged across hold / claim / expiry.
